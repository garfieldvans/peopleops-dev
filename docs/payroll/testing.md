# Payroll Testing

## Commands

```bash
pnpm --filter @peopleops/api test
pnpm --filter @peopleops/web test
pnpm --filter @peopleops/api test:e2e
pnpm -r typecheck
pnpm lint
pnpm build
```

The e2e suite requires PostgreSQL and applies migrations to the `peopleops_test` schema. Payroll
fixtures are removed by `apps/api/test/cleanup-test-data.ts` before each run.

## Unit coverage

`apps/api/src/modules/payroll/payroll.utils.spec.ts` covers:

- Decimal arithmetic without binary floating-point drift;
- `HALF_UP`, `ROUND_DOWN`, and `ROUND_UP` at currency scale;
- percentage calculation;
- UTC date-key round trips used for effective-date and period comparisons.

Existing API suites cover shared timezone, attendance, overtime, auth, and permission-guard behavior.

## Integration coverage

`apps/api/test/payroll.e2e-spec.ts` passes **8/8**:

1. One active run per period; duplicate creation returns `409`.
2. Base salary plus assigned fixed earning produces the expected gross and net.
3. Recalculation applies only approved adjustments and increments the calculation version.
4. Submit review → approve → publish records the workflow history.
5. Published payslips keep their compensation snapshot after a later compensation edit.
6. Attendance `ABSENT`, approved unpaid leave, and `VERIFIED` overtime produce source lines,
   source references, deductions, and the configured overtime multiplier. The same case adds a 10%
   percentage earning and a fixed employer contribution; expected gross `24581502.89`, deductions
   `3000000`, employer contributions `500000`, net `21581502.89`.
7. The register paginates rows (`pageSize=1` returns one row, `total=2`, `totalPages=2`) while its
totals still cover both payslips.
8. Employees can read/download only their own published payslip; another employee receives `403`,
   and the PDF response is a real `application/pdf` payload.

The full API e2e suite passes **49/49** across auth, employees, attendance, leave, overtime, and
payroll.

## Frontend coverage

`apps/web/src/features/payroll/payroll-pages.test.tsx` covers permission-denied rendering, published
payslip listing with formatted currency and PDF action, run-detail action visibility for an
`UNDER_REVIEW` run (approve visible, publish hidden), and the register tab showing range-wide totals
with server pagination metadata. The full web suite passes **38/38**.

The payroll screens include loading, error, empty, and permission-denied states, warning panels,
confirmation dialogs for calculate/approve/publish/cancel, and distinct badges for draft, calculated,
under review, approved, published, and cancelled runs.

## Known limitations

- Calculation runs synchronously in the API request; the worker only performs read-only payroll
  housekeeping (stale calculation, stale review, approved-but-unpublished counts). There is no
  queue because the current population fits a request-scoped transaction.
- Payslip PDF generation is on-demand and not pre-generated by the worker.
- Statutory tax, BPJS, THR, loans, reimbursements, bank transfer, and accounting journals are out of
  scope by design.
- Payroll frontend tests focus on access control and core run actions; every form field is not
  individually exercised.
